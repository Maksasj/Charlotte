# Report: the plan carried out, and what the chats now teach

24 November 2026. Continues [`report-2026-11-23.md`](report-2026-11-23.md). Covers
the `cbr` branch from the consolidated plan (tiers 0 to 4, without article
mining) to learning task intents from Schema-Guided Dialogue labels. The
earlier report's "what is still wrong" list is the starting point.

## In short

- Every item of the plan except article mining is built and pushed. Tests
  pass (14 integration, 1 unit); the real-chat regression score is −0.347.
- The first honest test on a clean vault showed the plan did **not** make the
  chat data useful: simulated learning worked, the real chats gave nothing,
  and the social labels taught bad phrases.
- The cause was that only SGD's social labels were used. Its task labels
  (intent, slots the agent asked for, values given) were still unused.
- They are used now. `charlotte tasks` learns task intents, their wordings,
  their slots and the order in which to ask them. On all 5,956 held-out SGD
  dialogues from a clean vault: intent read 78%, hand-over reached 74%.
- Still weak: values given in the first request are not extracted (so slots
  are asked again), and chit-chat recall is no better than before.

## What we discovered

**Unseen combinations need composed examples.** With call/return in place, an
engine trained without composed conversations got 0% on held-out combinations
and 100% with three composed demonstrations (23 composed conversations were
available). The mechanism works; the data has to show it.

**The clean-vault test.** A scratch copy of the vault with nothing learned,
scored on 12 rewordings:

| Stage | Rewordings read | Score |
|---|---|---|
| Nothing learned | 6 | −0.107 |
| + 9,000 simulated conversations | 8 | −0.133 |
| + DailyDialog chats as recall | 8 | −0.267 (recall right 23, wrong 43) |
| + SGD social labels, auto-promoted | 8 | −0.267 |

- Simulated learning works (100% on held-out simulated conversations).
- Recall on DailyDialog is mostly wrong. It is chit-chat, so it only stresses
  the fallback and says little about the task.
- Auto-promoting SGD's social labels produced bad phrases: "no that's all" and
  "nothing" became *thank*, so "no that's all" was answered "Anything else?".

**What SGD actually holds.** 22,825 dialogues, 46 task intents, 87 requested
slots. Each user turn labels the intent wanted and the values given; each
agent turn labels the slot it asks for. That is exactly the data for learning
a task, and it had been stored but not used.

**Learning a task from those labels** (candidates only, held out by SGD's
dev and test splits):

| Measure, 5,956 held-out dialogues, clean vault, no chats | Result |
|---|---|
| Intent read from the first request | 78% |
| Hand-over reached | 74% |
| Asked exactly the real agent's slots, in order | 71% |
| Slots we asked that the real agent asked | 55% |
| Slots the real agent asked that we also asked | 76% |

The first 1,500 dialogues gave 77% / 72% / 66% / 78% / 77%. The drop in the
fourth row on the full set shows later dialogues have the user volunteering
more values up front, which we do not yet extract.

## How `charlotte tasks` works

- **Wordings** come from the user's `INFORM_INTENT` turns: n-grams kept when
  they point at the intent often enough and the same holds on held-out
  dialogues (precision at least 0.5, 8 or more uses). Looser than first tried
  (0.7): intent read rose from 66% to 77%.
- **Required slots and order** come from the agent's `REQUEST` acts. A slot is
  required if asked in at least 40% of the dialogues of the intent; order is
  its average position.
- **Slot types** come from the values given: true/false, numbers, a closed set
  of at least two values (up to 12), otherwise free text. The ask text is the
  agent's own question most like the others.
- **An atom** per task with "slot given" conditions, so the existing
  check-a-rule pattern asks what is missing, then hands over. No change to the
  decision layer.
- **Engine change:** a short free-text answer (6 words or fewer, no other facts,
  not yes/no) to the slot just asked is bound as its value. Existing vault
  slots are all typed, so they are unaffected.

## What we fixed

- The `--promote` flag was consumed twice in the CLI, so scratch promotion
  silently did nothing and the first evaluation read 0%.
- Intent counts attributed a dialogue only to the last intent on a service;
  they now count every intent that appears.
- A closed set of one value was typed as an enum; it now needs at least two.

## What is still wrong

Ordered by how much it limits the agent.

1. **Values in the first request are not extracted.** "A restaurant in San
   Jose" is read as the task, but the city is asked again. Free text has no
   wording patterns. This is why only 55% of asked slots match the real agent.
2. **Similar tasks are confused.** 22% of first requests are not read as the
   right intent, mostly among Find, Search and Reserve variants.
3. **Chit-chat is not learned.** DailyDialog chats and SGD social labels
   still gave nothing useful, and recall is wrong more often than right.
4. **Free-text binding can store a wrong answer.** A short off-topic reply to a
   question can become the value.
5. **Slots are per task.** The same SGD slot (for example `city`) is a separate
   slot for each intent, so a value given for one task is not reused by
   another.
6. **Saved conversation state drops session entities**, so references would not
   survive a reload.
7. **Not tested with real users.** All numbers are against SGD's own held-out
   dialogues, whose agent replies and slot sets are what they are.
8. **Left out on request:** mining articles into atoms. Learned connectors found
   nothing on real data and are exercised only by a synthetic test.
